# Reading an interface without looking at it

## Audit line 1 — the keyboard path

Not a tab order. A **state machine**: at each state, what is reachable, and
where does focus go when the state changes underneath the user?

The classic failure:

```
[Cancel] has focus → upload completes → [Cancel] removed from the DOM
                   → focus falls to <body>, nothing announced
```

The user does not know it finished. They know their keyboard stopped working.

## Audit line 2 — semantics for a value you may not have

```html
<!-- determinate -->
<div role="progressbar" aria-valuemin="0" aria-valuemax="100"
     aria-valuenow="43" aria-valuetext="43% — transferring"></div>

<!-- indeterminate: omit the value -->
<div role="progressbar" aria-valuetext="Transferring, total unknown"></div>
```

`aria-valuetext` is for when the bare number is unhelpful — **"3 of 7 files"**
beats **"43"**.

**Omitting `aria-valuenow`** = indeterminate. **`aria-valuenow="0"`** = nothing
has happened. Different claims.

---

## Audit line 3 — the announcement flood

The failure mode is not silence. It is **volume**.

```js
bar.setAttribute("aria-valuenow", pct);
live.textContent = `${pct}%`;      // ✗ ~100 announcements per upload
```

```js
if (state !== lastState) {          // ✓ 4 or 5 per upload
  live.textContent = MESSAGES[state];
  lastState = state;
}
```

**Announce transitions. Never increments.** A bar that announces every integer
has not been made accessible — the three transitions that mattered are buried.

## Audit line 4 — reduced motion as a diagnostic

Usually taught as a courtesy. Treat it as a **test**.

```css
@media (prefers-reduced-motion: reduce) {
  .bar-fill { transition: none; animation: none; }
}
```

Turn it off, then ask: **what information left with it?**

If something did, that information was never in your interface. It was in the
animation, and an animation is not something everybody gets.

## Worked example — one defect, found and closed

Run the audit on the week 4 indeterminate treatment:

| Step | Finding |
| --- | --- |
| Listen | "progress bar **0 per cent**" |
| Read the DOM | `aria-valuenow="0"` on the unknown-length stream |
| Name the claim | it says *nothing has happened*; four stages have |
| Fix | drop `aria-valuenow`, add `aria-valuetext="Transferring, total unknown"` |
| Re-check | "progress bar, transferring, total unknown" |

Recorded as a **FAIL, then a fix**. Four passes and no notes reads as an audit
that was not run.

## The mistake to expect

Recording a pass you cannot demonstrate.

> A line recorded honestly as a **failure scores**.
> A line recorded as a **pass that your marker can break does not** — and costs
> more than the failure would have.

The second-commonest: fixing line 1 in a way that breaks line 3. Moving focus on
completion is correct; moving it **without announcing why** replaces a silent
failure with a confusing one. Re-run all four lines after any fix.

## What this week cannot tell you

Two people at adjacent desks are not a test of whether this works for the people
it excludes.

A checklist is a record of failures somebody has **already** had. It cannot
report one nobody has written down yet. Neither of you uses a screen reader
daily, so you have established the announcements exist and are sane — not that
they are good.

Write that sentence on the sheet.
